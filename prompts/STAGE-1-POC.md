# STAGE 1 — POC BUILD — argus-token-factory-gateway

Build a small, working multi-tenant inference service ("token factory" front door) and prove it on a real workload. This is Stage 1 of 3. Stage 2 (article) and Stage 3 (standalone HTML) consume this stage's run report and the raw artifacts exported in Phase 5; they cannot re-run anything, because Phase 5 destroys the infrastructure. Do not start Stages 2 or 3. Stop at each checkpoint and report.

Several behaviours below (RunPod pod networking, vLLM usage fields, LiteLLM parameter passing) are stated as verifications with fallbacks, not as assumptions. If a verification fails and no fallback works, stop and report.

## Repository

- Create a GitHub repo named `argus-token-factory-gateway` under the operator's account, PRIVATE. (It goes public only at launch, at the end of Stage 3.)
- Layout: `gateway/` (compose, shim, configs), `clients/` (tenant-a batch runner, tenant-b runner, `clients/agent/`), `workload/` (dataset preparation), `sources/` (operator-supplied documents, see the input check), `prompts/` (copies of the three stage prompts, with any review-process commentary stripped), `docs/` (reserved for the GitHub Pages site built in Stage 3; keep it empty of everything else, because Pages publishes the whole folder), `RUN-REPORT.md` at root.
- `.gitignore` must exclude `.env` at every level (`**/.env`) and any file containing keys, tokens, or salts. Secrets are never committed, never printed in reports; refer to them by variable name.
- Input check, first action: confirm `sources/` contains `framework-report.md`, `evidence-bank.md`, `evidence-refresh-2026.md`, and `cost-per-outcome.md`. If any is missing, stop and tell the operator; Stages 2 and 3 depend on them.

## Fixed design (do not redesign)

- One shared inference endpoint: a RunPod pod (RTX 4090) running vLLM, serving **Qwen/Qwen2.5-Coder-7B-Instruct**. The model choice is justified from `sources/cost-per-outcome.md` (it won two of the author's three measured workloads at the lowest cost per outcome); cite that file in the run report. Tenants never reach the pod directly.
- Pod networking: the pod must be reachable from the droplet over a stable, controlled path, and the run report must state which path was used and what the claim "tenants never reach the pod" rests on:
  - Preferred: pod with a public IP and TCP port mapping; the droplet's egress rules pin that IP and port, and vLLM runs with `--api-key` so the port rejects unauthenticated calls. Note that Community Cloud pods often have no public IP, in which case the fallback below is the expected path.
  - Fallback: a Tailscale overlay between droplet and pod. RunPod pods have no `/dev/net/tun`, so the pod side must run tailscaled in userspace networking mode (`tailscaled --tun=userspace-networking`), with vLLM reached through the overlay (for example via `tailscale serve` or the userspace forwarder), and the end-to-end path verified in Phase 0.
  - The default `*.proxy.runpod.net` URL alone does not satisfy this requirement; it is a public front door in its own right.
- Gateway on one DigitalOcean droplet (Basic, 4 GB RAM, Ubuntu 24.04; add a 2 GB swap file), Docker Compose: Caddy, auth shim (FastAPI + PyJWT; a single small service, a few hundred lines), LiteLLM OSS, Postgres. Pin every image to a specific version tag (never `latest`) and record the versions in the run report. Caddy is the only service that publishes host ports, and it routes only `/v1/*` to the shim; every other path returns 404. LiteLLM publishes no host port; only the shim reaches it, on the internal Docker network, so LiteLLM's `/key/*`, `/user/*`, and `/ui` are never public. LiteLLM's master key exists only in the droplet's `.env`.
- Public name: `factory.harishparam.com` (DNS A record to the droplet; the operator creates the record — flag it as an operator action).
- The shim fronts every call, on every identity path. It resolves the principal (tenant, identity mode, subject, actor), overwrites `cache_salt` with the tenant's secret salt (never client-supplied, on all paths including factory keys), caps max_tokens, forwards to LiteLLM with the principal's key, and writes the audit row. For factory-key calls it maps the presented key to its tenant from the operator registry before doing the same. The operator registry, including every tenant salt, is configuration sourced from the environment (the droplet's `.env`); a registry template with placeholder values may be committed, a populated one never. The shim has one test-only flag that disables salting; it defaults to on (salting active), exists solely for the D2 control sequence, and every use of it is recorded in the run report.
- Identity: Tenant A uses a factory-issued LiteLLM virtual key. Tenant B federates through ZITADEL Cloud (free tier): the shim validates its JWTs per issuer (JWKS per issuer, asymmetric algs only, exact iss/aud/exp) and maps (iss, claim) to the tenant from the operator registry only; subject claims in headers are never trusted.
- Client C is a live agent acting for Tenant B's user. It runs **from the operator's Mac** (script in `clients/agent/`; its ZITADEL machine credential and the user's refresh token live in the Mac's local `.env`), never on the droplet: the agent is a customer-side caller and must cross the public front door like one. The user's token is obtained through ZITADEL's device authorization flow (or authorization code with PKCE and a local redirect), so the script can renew it without an interactive login each run. Flow: user token from ZITADEL + the agent's own credential → token exchange producing sub=user, act=agent → calls through the gateway. Rate limiting is per actor, implemented as a dedicated LiteLLM key for the agent under Tenant B's team budget; the tenant budget (team level) counts the user key and the agent key together, while the agent key's own RPM limit throttles the agent alone. If ZITADEL's token exchange is unworkable, the fallback is the shim minting a short-lived internal delegation token after validating both credentials; the shim still forwards with the agent key; record which path was used.
- Audit: the shim writes an intent row per call (timestamp, tenant, identity mode, subject, actor, model, call id, rejected flag) at request time, including rejected calls, which never reach LiteLLM. Token and cost figures are joined in afterwards from LiteLLM's SpendLogs by call id; the shim does not recompute cost. POC calls are non-streaming; streaming accounting is out of scope and the run report says so.
- Workload (the working example): **QASPER** (Allen Institute; Hugging Face `allenai/qasper`). Papers carry only ~3 questions each, so the workload is a fixed set of papers totalling at least 30 questions; record the paper IDs. Both tenants run the same papers. Every call carries the full paper text as the shared prefix plus one question. During workload preparation, tokenize each candidate paper: a paper is eligible only if its full text plus question plus the answer budget fits the served context window with margin. Set vLLM's `--max-model-len` explicitly in the pod spec and record it; do not rely on the model's default. Load the dataset from its parquet conversion (or a pinned revision), pin the loader and library version, and record the exact source and the dataset license from its card. Scoring: token F1 per question, taking the maximum over annotator answers; yes/no questions and unanswerable questions are reported as separate counts with their rule stated, not folded into F1.
- Layer scope: this POC exercises identity and gateway. There is no sandbox layer: no consumer code executes on factory infrastructure. State this in the run report in one paragraph.
- Droplet egress is default-deny, **enforced in the DOCKER-USER chain** (Docker bypasses host ufw rules; do not rely on ufw alone). Egress is by IP, so hostname-based destinations are handled explicitly: at setup, resolve the ZITADEL issuer host and the ACME endpoints to an ipset, refresh the ipset on a timer and again before the demo runs, and record the refresh method in the run report. Per container: LiteLLM and Postgres need only the pod address and the internal network; the shim needs the pod path (via LiteLLM) plus the ZITADEL JWKS endpoint; Caddy needs the ACME endpoints (outbound 443, inbound 80/443 for certificates). Name resolution is an explicit allowance: containers may reach the droplet's configured resolver on port 53 (Docker's embedded DNS forwards upstream there), since without it the allowlisted hostnames cannot be resolved at all. A request from any container to an unlisted destination must fail; verify one in Phase 0.

## Phase 0 — Preflight (STOP for operator approval before creating paid resources)

1. Input check (above). Then list the exact paid resources about to be created (droplet size/region/price; RunPod pod tier/price, with at least 40 GB of pod disk for the model weights and cache) and get the operator's go. Pod tier: try Community Cloud ($0.34/hr) first; fall back to Secure ($0.89/hr) if stock fails; record which. Create the pod first, note its datacenter, then choose the droplet region nearest to it.
2. Pod networking per the fixed design: establish the public-IP path or the userspace-Tailscale path, verify the droplet reaches vLLM end to end, and (public-IP path) verify an unauthenticated call to the port is rejected via `--api-key`.
3. vLLM checks, at the pod level (the gateway chain does not exist yet): version is 0.9.0 or later (cache_salt support); server started with `--enable-prompt-tokens-details` (without it, usage carries no cached-token counts), `--max-model-len` set per the workload ceiling (tokenize the candidate papers as part of this step to set it), prefix caching enabled. Direct-call cache test against the pod: same long prefix twice under one salt shows cached tokens on the second call; the same prefix under a second salt shows ~0. If cached-token counts are absent or salts do not separate, this is a hard stop: report, do not fake the cache demo.
4. Pricing: the pod is flat hourly, so derive the LiteLLM model price (pod $/hr divided by measured tokens/hr) and record the derivation, stating the measurement conditions: tokens/hr measured with a single sequential client, matching how the demos run. Apply the resulting rate as both the input and output per-token price (a blended rate), and say so. If the derived price is left at zero, budgets read $0 and Demo 1 cannot fire; that is a Phase 0 failure.
5. Egress: build the ipsets, apply the DOCKER-USER rules (including the DNS allowance), and verify name resolution plus one allowed destination (ZITADEL JWKS from the shim container) and one disallowed destination (any unlisted host, which must fail).
6. DNS: the subdomain resolves to the droplet. The TLS certificate check runs when the compose Caddy starts in Phase 1, and is recorded there.

## Phase 1 — Gateway and Tenant A

- Compose stack up with health checks, all images pinned; 2 GB swap file created; LiteLLM configured with the pod as backend at the Phase 0 price.
- Phase 1 exit gate (before any tenant work): rerun the two-salt cache test through the full chain (shim → LiteLLM → vLLM) and confirm the cached-token counts still separate by salt, and that LiteLLM's own response caching is OFF. If either fails here, stop and report; the D2 demo depends on both.
- Tenant A virtual key: model allowlist (the one model), small budget with short budget_duration, RPM/TPM limits, key expiry set.
- Tenant A batch runner (`clients/tenant_a_batch.py`): runs the QASPER workload set, writes per-question results (answer, tokens, cost, F1) to a results file.
- Smoke tests: a workload call succeeds with nonzero logged cost; a non-allowlisted model is rejected.

## Phase 2 — Tenant B federation and the agent

- ZITADEL: one organisation for Tenant B, one user, one project/application; prepare the exact values the shim needs (issuer, audience). Operator creates the account; you prepare the click path. Create Tenant B's user with a dedicated demo email address, not the operator's personal email: the audit export becomes public at launch and will carry the subject identifiers.

- Team budget verification: with a disposable test key, confirm the team-level budget actually blocks a call once exceeded in this LiteLLM version. If team budgets do not enforce in the OSS build, fall back to per-key budgets whose sum equals the tenant cap (user key and agent key), and record the substitution in the run report; D3's wording follows whichever mechanism is live.
- Agent (`clients/agent/`): obtains the delegated token, then completes one task for the user: answer 3 QASPER questions and produce a short answers brief. Runs from the operator's Mac against the public gateway URL.
- Negative tests: expired token, wrong audience, unregistered issuer, tenant claimed by header only — all rejected (401), and each rejection appears in the audit table with the rejected flag set.

## Phase 3 — The demos (on the workload, scripted and repeatable)

Demo state: each demo sets its own gateway state (budgets, limits, cache state) before it runs, and the run report records the state per demo. In particular, after D1 exhausts Tenant A's budget, reset or raise it before D2 and record the reset; a blocked Tenant A in D2 is a setup failure, not a result.

- **D1, budget cap fires mid-work.** Size Tenant A's budget from Phase 0's measured per-call cost so the stop lands between 40% and 70% of the batch. Run the batch sequentially. LiteLLM records spend after each call completes, so expect the cap to overshoot by at most the calls in flight; with a sequential batch that is one call. Record the actual overshoot rather than treating it as an anomaly. Capture: questions answered vs the rejection, the spend rows proving the cap stopped the batch.
- **D2, cache isolation, two sequences.** Note on mechanics: a salted cache entry is keyed by the salt, so a request under a different salt, or with no salt, cannot hit it. The two sequences are therefore designed as follows.
  - *Main sequence (salting on):* designated paper, declared cold state (restart vLLM first if the paper has been served before; record the restart). Tenant A runs the paper and warms its cache (report cached-token share). Tenant B runs the identical paper and questions: first pass must show ~0 cached tokens; Tenant B's repeat shows its own cache working.
  - *Control sequence (salting off):* restart vLLM so the cache is cold. Set the shim's test-only salting flag off. Tenant A runs the paper, warming the unsalted cache. Tenant B runs the identical paper: its first pass now shows Tenant A's warm cache (high cached tokens). Set the flag back on. Record the flag's use, the restart, and both sequences in the run report; the comparison that carries the claim is Tenant B's first pass, salted (~0) versus unsalted (warm).
  - Timings: report medians of at least 5 runs for repeat (steady-state) passes. First passes are single measurements by construction — a second attempt is no longer a first pass — and are reported as singles. Cached-token counts are the primary evidence throughout; timings are secondary.
- **D3, the agent works under delegation.** The agent completes its 3-question brief from the Mac. Then loop the agent rapidly until its key's rate limit returns 429; during the throttling, make one Tenant B user call and show it still succeeds, and show the team budget (or the summed per-key budgets, per the Phase 2 verification) reflects spend from completed calls only. Capture all three facts.
- **D4, audit reconstruction.** One query listing every call from D1-D3 grouped by tenant, identity mode, subject, and actor, with token and cost totals, plus the rejected calls from Phase 2 listed separately. This output is reproduced in the run report verbatim.

## Phase 4 — Run report (`RUN-REPORT.md`, the Stage 2 input)

- What was built, component by component, with repo paths. Pinned versions of vLLM, LiteLLM, Postgres, Caddy, and the dataset loader.
- Phase 0 facts verbatim: pod tier and price, pod datacenter and droplet region, the pod networking path used and what enforces it, vLLM version and flags (including `--max-model-len`), cache evidence from both the pod-level test and the Phase 1 exit gate, the derived model price with its derivation and measurement conditions, DNS state and where TLS was verified, where the egress rules live and how hostname destinations are handled.
- Demo outputs verbatim, including D1's actual overshoot, D2's two sequences with the cold-state procedures and the salting flag's use, and every per-demo state reset. QASPER results per tenant run (papers, question counts, F1, the yes/no and unanswerable counts with their rules), dataset source and license. State plainly that the served model is a coder model selected from the author's earlier cost-per-outcome measurements (`sources/cost-per-outcome.md`), and that F1 here shows the workload ran, not a model-quality claim.
- Cost ledger: droplet hours and cost, pod hours and cost, IdP $0. Every number traced to a bill, log, or config.
- Time per phase, honestly totaled. Timings live in this report only; they are internal record, and Stages 2 and 3 must not surface them.
- Pitfalls and resolutions. Scope paragraph (layers exercised / not exercised; paths A, B, C live, D framework-only; non-streaming scope note).
- Prose style: plain language, no em dashes, no contrast-framing constructions, no marketing diction.

## Phase 5 — Export and teardown

- Export into the repo everything Stages 2 and 3 might quote, because nothing can be re-run after teardown: the full audit table (CSV or SQL dump; strip LiteLLM's hashed key-token values and any prompt or response content if present — before exporting, verify what the SpendLogs rows actually stored and record the finding in the run report; the export deliberately retains ZITADEL subject IDs and the demo organisation name, which become public at launch), the per-question results files for every run, the raw demo outputs, the final billing figures for the droplet and the pod, and the as-run configs with secret values removed. The ledger in `RUN-REPORT.md` is completed from these exports before anything is destroyed.
- Preserve the sweep reference copy before destroying anything: copy the droplet's `.env`, the pod's vLLM `--api-key` value, the Tailscale auth key (if the overlay path was used), the full values of the generated LiteLLM virtual keys (Tenant A, Tenant B user, and agent; they exist only as hashes in Postgres and in the runners' local `.env` files, and are destroyed with the droplet), and from the Mac's `.env` the ZITADEL machine credential and the user's refresh token, into a single local file outside the repo, at a gitignored path on the operator's machine that is never committed. Stage 3's launch sweep greps the git history against this copy; once the droplet and pod are destroyed, the salts and keys they held exist nowhere else, and a sweep with nothing to compare against is theatre. Record the copy's location (path only, never contents) in the run report. The copy is deleted after launch, in Stage 3's final step.
- With operator confirmation: destroy the pod and the droplet; note the DNS record as an operator removal. Record the teardown in the run report. After teardown, `factory.harishparam.com` no longer serves a live endpoint, and every later description of the POC (article, README, HTML) must present it as a completed run. If the operator elects to keep anything running, record that instead, with its hourly cost.
