Token Factory: the framework, the evidence and the proof of concept

A token factory sells inference as a metered service. This page holds the detail behind a proposal for building one: the design in full, the evidence for five tenets, and the complete record of a small instance that I ran once and then shut down.

Status. I stood up a proof of concept to replicate the framework as closely as a small instance allows, then ran a real workload through it to test and validate the design. No endpoint is live. The repository holds the configs, the run report and the raw exports, which are the evidence.

1Overview

The proposal is written from the provider's side of the counter. Customers send prompts, the factory runs them on shared GPUs, and customers get completions and a bill. Five tenets describe the terms on which the factory sells.

Lowest cost

Choose the model and the hardware by cost per outcome, and meter at a price that reflects what the hardware costs.

Federate with the customer's identity provider

Customers sign in with the identity they already run. Where a customer cannot federate, the factory issues scoped credentials and gives the tenant an admin path to revoke them.

Isolate each tenant's data and cache

One tenant's prompts must leave no trace another tenant can measure.

Meter and manage spend

Every call is metered to the tenant, the user and the agent behind it, and a cap refuses the next call once the budget is gone.

Audit every call

Every request leaves a row that says who made it and on whose behalf.

2The framework in full

The design rests on one idea. Every identity path resolves to the same principal record before anything else happens, and every downstream control reads that record and ignores the raw request.

2.1 The resolved principal

The principal carries a tenant, an identity mode, a subject, a key or client id, an optional actor, the allowed models and a budget account. The budget check, the model allowlist, the cache salt, the rate limit and the audit row each take their key from this record. A client-supplied tenant header never enters it.

{ tenant_id, identity_mode, subject, key_id | client_id, actor?, scopes/models, budget_account }

2.2 The four identity paths

Live(a) Factory-issued credentials API keys or OAuth client credentials. In the proof of concept: Tenant A.

Flow. The operator, or a tenant admin through a portal, requests a key. The gateway mints a virtual key bound to a tenant and shows it once. The tenant's service sends it as a bearer credential. The gateway hashes the key, looks it up, loads its policy (models, budget, rate limits, expiry) and forwards to the model with a credential the tenant never sees.

Validation and storage. Keys are random and at least 256 bits, with a recognisable prefix and a short non-secret id for lookup. Only a hash is stored. For high-entropy machine keys a fast hash such as SHA-256, ideally HMAC-SHA-256 with a server-side pepper, is the standard pattern, because slow password hashes suit low-entropy human passwords. The gateway master key is never a tenant credential. Rotation runs as issue new, overlap, revoke old, with one key per application so that revocation reaches one application.

Budget and audit. Spend attributes to key, user and team in the spend ledger. The audit row carries the key hash prefix, the tenant, the model, the tokens and the cost.

Pitfalls. Key leakage into repositories, logs and client bundles. Keys with no budget, which is the denial-of-wallet case (OWASP LLM10, unbounded consumption). Shared keys that destroy attribution. Rotation that needs downtime because only one active key per tenant was designed in. Exposure of the master key.

Live(b) Federated identity provider The tenant's own Okta, Entra or Google over OIDC. In the proof of concept: Tenant B, through ZITADEL Cloud.

Flow. The tenant admin registers the factory as a relying party in their identity provider, or the factory registers a client in a tenant-dedicated realm. A user or service obtains a token from that provider, with authorization code and PKCE for people and client credentials for services, and calls the gateway with the JWT. The gateway validates it, maps its claims to a tenant and applies policy and budget as in path (a).

Validation.

  • Signature against the issuer's published key set, selected by key id. Asymmetric algorithms only; HMAC algorithms are rejected.
  • Issuer: exact string match. A trailing slash and the scheme both matter.
  • Audience must contain the gateway's audience. Expiry and not-before are checked with a small clock-skew allowance of 60 seconds or less.
  • Tenant comes from an operator-controlled registry keyed on issuer and subject. A valid token from Tenant B's provider must be unable to assert Tenant A's id.

Key-set caching matters. A gateway that caches the key set for its time-to-live and does not refetch on a key-id miss will reject a just-rotated key until the cache expires. With several issuers, a shared key list that selects by key id alone can verify only one issuer and audience, so the issuer must be verified per provider and unlisted issuers must be rejected.

Budget and audit. The resolved tenant maps to a team created out of band. The audit row carries issuer, subject, tenant and the identity mode.

Pitfalls. Accepting ID tokens in place of access tokens, which gives the wrong audience. Not verifying the issuer when several providers are configured, so that any provider can impersonate. Algorithm confusion. Outages from key-set rotation against fail-open stale keys. Subject values collide across providers, because a subject is unique only per issuer. Tenant onboarding friction (redirect URIs, custom domains, availability of the tenant's identity admin) is the schedule risk. Group-claim overage in large directories.

Live(c) Delegated agent An agent acting for an end user. In the proof of concept: Tenant B's agent.

Flow, single trust domain. The user authenticates to their identity provider, and the agent obtains the user's token. The agent calls the provider's token endpoint with the RFC 8693 token-exchange grant, passing the user's token as the subject token and optionally its own token as the actor token, with an attenuated audience and scope. The provider returns a short-lived token whose subject is the user and whose act claim names the agent, with nested act claims for chains. The agent presents that token to the gateway, which validates it as in path (b) and extracts act.

Cross-domain variant. When the agent and the resource sit in different trust domains, the pattern standardised in the IETF draft on identity assertion authorization grants (draft-ietf-oauth-identity-assertion-authz-grant, revision 04 dated 2026-05-21) chains two exchanges: an RFC 8693 exchange at the user's identity provider that yields an identity assertion, then an RFC 7523 JWT-bearer grant at the resource's authorization server. Consent and policy live at the identity provider. It is a 2026 draft, so a factory should implement RFC 8693 act-claim support first and treat this as the cross-domain upgrade path.

Validation. Both identities independently: the user (subject, tenant from the user's issuer) and the agent (act.sub or the agent's client id). Authorisation is the intersection of the agent's allowed models, the user's allowed models and the tenant policy. Scopes may only narrow across an exchange. The gateway rejects exchanges that widen scope, tokens that lack act when an agent is present, and a raw user session token forwarded by an agent, which is the token-passthrough anti-pattern this mode exists to replace.

Budget and audit. Spend charges the tenant or user account. Rate limits and anomaly alerts attach to the agent as well. Audit rows carry the user as subject, the agent as actor and the delegation depth. Either identity must be revocable alone: removing the agent's registration must not reset the user's credentials, and the reverse.

Pitfalls. Confused deputy, where an agent is tricked into using its delegation for another user (bind tokens to the agent's key where possible, for example with DPoP or mutual TLS). Recursive or unbounded delegation chains, so cap act nesting, typically at 1. Long-lived delegated tokens, which should last minutes. Audit rows that record only the user, which makes agent abuse unattributable.

What ran. The identity provider instance did not advertise token exchange, so the proof of concept used the fallback in the design: the gateway validated the user's token and the agent's token and minted the delegation token itself. Section 5 shows the call.

Design(d) Trial tier Email-verified or anonymous, hard-capped. Not built.

Flow. Sign-up with email verification (magic link or one-time code) or an anonymous session. The factory mints a trial-scoped credential, the gateway enforces the trial policy, and on exhaustion the caller gets a hard 402 or 429 with an upgrade path and no silent overage.

Controls. A tiny total budget (for example $0.50 to $2, not resetting by default), one cheap model, low request and token rates, small max_tokens and context limits, a credential lifetime of hours to days, one trial per verified email plus payment and network heuristics, a bot check at sign-up, and minimal content logging. The trial account is separate from paid accounts, so trial burn can never consume a paying tenant's budget. The audit still stamps every call, because trial traffic is where abuse telemetry comes from.

Pitfalls. Sybil farming with disposable emails, and anonymous trials that work as an open proxy and get found by scanners within hours. Scripts that use trial keys as a free inference API, so cap tokens per request and in total, not only the request rate. SMS one-time codes are the classic toll-fraud vector, so prefer email links. The hard cap must account for in-flight concurrency.

2.5 Isolation and request hygiene on shared inference

  • Prefix-cache salt. Automatic prefix caching reuses cache blocks for shared prompt prefixes, and a hit is visible as a faster first token. A per-request cache_salt is mixed into the hash of the first block, and every later block hashes from its parent, so only same-salt requests share blocks. vLLM's documentation says the salt should be random, secret and unpredictable, around 256 bits.
  • The gateway owns the salt. The salt derives from the authenticated tenant (a stored per-tenant secret, or an HMAC of a server secret and the tenant id). The gateway strips any salt the client sends and overwrites it. The same treatment applies to multimodal uuid values and kv_transfer_params. Salts rotate on tenant off-boarding or key compromise, at the price of a cold cache for that tenant.
  • Honest limits. vLLM's documentation says it does not isolate tenants that share a server process, and that the salt is not an isolation boundary. Tenants still share the scheduler and the GPU, a noisy neighbour can degrade latency, and timing channels beyond the prefix cache stay open. Full isolation is a dedicated instance per tenant.
  • Response caching. A response cache keyed on prompt content serves one tenant's answer to another. Keep the gateway's response cache off on multi-tenant routes, or include tenant, identity and model version in the key. Semantic caching across tenants is ruled out.
  • Payload validation before the model. Schema and size caps, an allowlist of parameters, caps on max_tokens, n and context length, an allowlist of media domains for image inputs, removal of upstream-identity fields, and a per-tenant concurrency cap so one tenant cannot fill the shared batch.
  • Upstream hardening. vLLM's --api-key protects only the /v1 family of paths. Other paths, including metrics and cache-reset endpoints, answer without a key. The model endpoint should be reachable only from the gateway, and the gateway should allowlist paths. In the run, the gateway proxied /v1/* only and answered 404 for every other path.

2.6 The audit record

One append-only row per request, written by the gateway before it forwards the call, not inferred later from a vendor bill. The framework lists these fields: request id, timestamp, tenant, identity mode, subject, actor if any, model requested and served, prompt, completion and cached tokens, cost, a salt identifier (never the salt), latency, status and the policy decisions. Metadata audit is not content logging: prompt and response bodies are stored separately, encrypted, for a short time, or not at all. The proof of concept stored none.

2.8 Reviewer security checklist

  • Keys are hashed, shown once, never logged, and the master key is kept apart.
  • The model-side key exists only in gateway secrets.
  • Per-issuer issuer and audience are enforced, HMAC algorithms are rejected, key rotation is tested, and the fail-closed or stale-key policy is a deliberate choice.
  • Clock skew is 60 seconds or less, expiry and not-before are checked, and token lifetimes are short.
  • JWTs are bearer credentials: short expiry bounds replay, and a token-id denylist is reserved for high-value operations. API-key replay is bounded by budget and allowlist. Sender-constrained tokens suit agent mode.
  • The cache salt is overwritten server-side, secret per tenant, and a cache-isolation test runs in CI.
  • Client-supplied kv_transfer_params, media ids and extra parameters are stripped.
  • The gateway response cache is off or tenant-keyed.
  • The model endpoint is not directly reachable by tenants, and paths outside /v1 are blocked.
  • The budget hard-stop is tested under concurrency, with in-flight overshoot bounded by max_tokens caps.
  • Every request gets an audit row, rejections included, with identity mode and actor. Prompt bodies stay out of audit logs.
  • Trial anti-abuse controls exist. TLS is used everywhere, and the admin UI is not public.
  • The database is backed up, a restore has been rehearsed, and secrets are kept out of the backup.

3.1 Isolate each tenant's data and cache

Why it matters. The prefix cache that makes shared inference fast also gives callers a timing side channel. An adversarial tenant can try to reconstruct another tenant's prompt from cache-hit latency, and published attacks report success rates from 89% up to 100% against unprotected servers. The attack needs only ordinary API access. The channel has a tracked CVE in vLLM. AWS's SaaS guidance states the architectural rule that isolation is a separate mechanism from authentication.

A shared cache lets one tenant probe another's prompt

KVGov reports a timing side channel in multi-tenant KV caches and cites three published attacks (PromptPeek, EarlyBird, InputSnatch) reaching up to 100% success against unprotected vLLM and SGLang. Measured on Qwen2.5-7B-Instruct with vLLM on an A100, a 2,119-token prefix took 149.6 ms to first token cold and 32.8 ms cached (a ratio of 0.22). Per-principal cache salting kept about 93% of the prefix-cache benefit.

Tejasvi C. Addagada, "KVGov", arXiv:2608.09225v1, 10 August 2026. arxiv.org/abs/2608.09225v1

CaveatSingle-author preprint. The defence was evaluated in simulation.

The attacks need no privileges

Chu et al. describe global KV-cache sharing as an API-visible timing channel. Their tabulation reports PromptPeek at 99%, 98% and 95% success (input, template and whole prompt), EarlyBird at 89%, and InputSnatch from 43.33% to 100% across 13 legal domains. The attacker interacts only through the standard API.

Chu et al., "Selective KV-Cache Sharing to Mitigate Timing Side-Channels in LLM Inference" (SafeKV), arXiv:2508.08438v2, 2025. arxiv.org/html/2508.08438v2

CaveatPreprint. The figures are as tabulated by the authors.

The channel is a tracked CVE

CVE-2025-46570 (advisory GHSA-4qjh-9fv9-r85r, published 29 May 2025, CWE-208) covers vLLM before 0.9.0. Cache-hit detection from time to first token reached an AUC of 0.571 with a 1-token prefix and 0.99 with an 8-token prefix. The fix, in 0.9.0, is cache salting.

Via the Wiz vulnerability database summary of the GitHub advisory. wiz.io/vulnerability-database/cve/cve-2025-46570

CaveatCVSS v3.1 base score 2.6, rated LOW, because the attack is complex. Cite it for existence and measurability, not for severity.

Isolation is separate from authentication

The whitepaper says SaaS systems need explicit mechanisms that isolate each tenant's resources even on shared infrastructure, and that an authenticated and authorized user can still reach another tenant's resources unless tenant context is enforced.

AWS, "SaaS Architecture Fundamentals" whitepaper, 3 August 2022 (foundational). AWS whitepaper (PDF)

3.2 Audit every call

Why it matters. Logging is becoming a legal property of AI systems. The EU AI Act asks for automatic recording of events and for retention of at least six months, and its high-risk obligations are deferred to 2027 and 2028. Practice trails the direction: most enterprises in one survey have agents running that they do not know about. A service that audits every call by construction closes the gap the surveys measure.

The law asks for automatic logs

3.3 Federate with the customer's identity provider

Why it matters. Attackers sign in. Valid-account abuse sits behind a large share of cloud incidents, password spraying dominates cloud initial access, and the 2026 reports describe attackers pivoting as MFA and passkeys spread. A service that federates inherits the customer's own sign-in controls, lifecycle and revocation, instead of adding its own passwords to the blast radius. Standards point the same way.

Some customers cannot federate. Where a customer cannot, the factory issues scoped credentials of its own and gives the tenant an admin path to revoke them. The proof of concept ran long-lived factory keys for Tenant A; short-lived credentials are a design claim and were not tested.

Legitimate access becomes the threat

Password spray accounts for over 99% of observed cloud initial-access efforts, in 124,146,529 password-spray attacks seen in Defender XDR data from December 2025 to June 2026. Overall password attacks fell 26% year on year, which the report attributes to MFA and passkeys forcing a pivot. The share of adversary-in-the-middle phishing and token theft more than doubled in the first six months of 2026. Of intrusions that began with valid accounts, 52.2% involved follow-on credential theft and 18.4% involved active password spray.

Microsoft, 2026 Digital Defense Report, "Decoding emergence" (July 2025 to June 2026), published 1 October 2026. Report (PDF) and launch post.

CaveatThe 99% figure is scoped to cloud initial access, not to all identity attacks. Microsoft's 73.3% figure (of initial-access attempts involving user execution, valid accounts, social engineering or phishing) comes from its 13 October 2026 summary. Phishing appears as 23% of intrusions in the incident-response data and as 11% in the Defender Experts data; the two are separate datasets and are not merged here.

Most detections involve no malware

82% of detections were malware-free, as adversaries used valid credentials, trusted identity flows and approved SaaS integrations. Valid-account abuse accounted for 35% of cloud incidents, and cloud-conscious intrusions rose 37%.

CrowdStrike, 2026 Global Threat Report, 24 February 2026; still the latest edition on 27 October 2026. crowdstrike.com

Exploitation has overtaken stolen credentials

From more than 31,000 incidents and more than 22,000 confirmed breaches in 145 countries, exploitation of vulnerabilities is now the most common initial access vector at 31%, and credential abuse, the previous leader, fell to 13%. Verizon notes this is the first time in 19 years that exploitation has passed stolen credentials.

3.4 Meter and manage spend

Why it matters. Consumption-priced inference fails open. One runaway agent loop produced a roughly $50,000 bill in under an hour, 93% of organisations in a McKinsey survey report exceeding AI budgets, and surveys show policy without real-time visibility. A cap enforced where spend is recorded refuses the next call, and a policy document does not.

One loop, about $50,000 in under an hour

A financial-services provider's ledger-reconciliation agent, with read and write access to billing databases, hit a corrupted null value and entered a recursive reasoning loop. In under an hour it made over 15,000 reasoning API calls, and the bill spiked by about $50,000.

Mandiant and Google Cloud, "AI Risk and Resilience in 2026", September 2026. cloud.google.com

3.5 Lowest cost

Why it matters. Inference has become the budget. It is the majority workload for most startups and about half of enterprises, enterprise AI spend more than tripled in a year, and 98% of FinOps respondents now manage AI spend. Cost is driven by task structure as well as token price. A factory's cost position is a first-order competitive fact.

The gateway can apply cost-per-outcome selection on every call. With automatic routing on, it classifies each request and sends it to the cheapest model that meets the tenant's quality setting, with the measured per-use-case picks as the default policy. If the chosen endpoint fails, the route falls back to a model the tenant designated in advance. The proof of concept routed by task, tenant policy and the principal's allowlist and did not test routing or failover.

4.2 The pod networking path and egress placement

The pod was reached through a public IP with a TCP port mapping to container port 8000, which was the preferred RunPod path. The overlay network (Tailscale) was prepared and not needed. The proxy hostname that RunPod also offers was not used.

Enforcement. The gate was vLLM's --api-key. From the droplet, an unauthenticated model-list call returned 401, an unauthenticated chat call returned 401, a wrong key returned 401, and the correct key returned 200 with the one model and a 16,384-token context. The /health path answered 200 without a key, because vLLM does not protect it. The port was reachable from the public internet, the API key was the only gate, and RunPod offers no IP allowlist. For that reason, "tenants never reach the pod directly" rests on the key and on tenants never holding it.

Egress placement. Rules sat on the droplet in the DOCKER-USER chain, through a dedicated chain, matched by source container:

SourceAllowed destination
LiteLLMThe pod's address and port only
ShimThe identity provider's hostnames, on port 443, through a hostname set
CaddyThe certificate authority's hostnames, on port 443
All containersThe droplet's upstream resolver on port 53, and the internal subnet
Everything elseRejected

Hostnames resolved into address sets that refreshed at boot, every 15 minutes and before each demo run. Inbound traffic to published ports was not filtered by this chain, and the droplet host itself was not filtered, because setup needed package registries. Only container egress was default-deny. Checks from throwaway containers with the static addresses: the shim reached the identity provider (302) and was blocked from example.com and from the pod; LiteLLM reached the pod's /health (200) and was blocked from example.com; Caddy reached the ACME directory (200) and was blocked from the identity provider's domain.

The price derivation

All 33 workload questions ran sequentially from the droplet against the pod, with one salt, max_tokens 256, which are the demo conditions. The run took 96.67 seconds of wall time and used 119,269 prompt tokens (108,000 cached) and 2,161 completion tokens, 121,430 in all. That is 4,522,034 tokens per hour. Dividing $0.897 per hour by that rate gives $1.9836e-07 per token, about $0.198 per million tokens, applied as one blended rate to input and output tokens, cached tokens included. One workload call at that point was estimated at about 3,680 tokens and $0.00073. The price rests on one sequential client and a mostly cached prefix, so it is a flat-rate allocation of the pod's hourly cost.

4.4 The gateway stack and Tenant A

  • Pinned images: Caddy 2.8.4, Postgres 16.4, LiteLLM v1.105.7, and a shim built from python:3.12.7-slim with fastapi 0.115.2, uvicorn 0.32.0, httpx 0.27.2, psycopg 3.2.3 and PyJWT 2.9.0. Health checks passed on all three services that had one. Memory after start was 1.2 GB of 3.9 GB, with 2 GB of swap present.
  • LiteLLM config: one model, the pod as backend, the derived price of 1.9836e-07 per token for input and output, response cache off, telemetry off.
  • The shim's factory-key path: the SHA-256 of the presented key is looked up in the registry to find the tenant and subject. Unknown or missing credentials returned 401 and were audited as rejected. Streaming requests returned 400 and were audited as rejected. A client-supplied cache_salt was dropped and replaced with the tenant's. A test-only switch could turn salting off, and it defaulted to on.
  • The audit join: the shim wrote an intent row before forwarding (tenant, identity mode, subject, actor, model, rejected flag and reason) and updated it afterward with the HTTP status and the response id. Cost and tokens join from the spend log on that response id. Rejections made by LiteLLM, such as a non-allowlisted model (403) or a budget refusal (422), are audited with the real status and a rejected flag of false, because only shim-level rejections carry the flag.

4.5 Federation and the identity tests

  • ZITADEL setup: one organisation, one project, one device-code application, a machine user named agent and a demo user with a dedicated email address. The organisation domain used for login names is a separate value from the instance domain that serves as the issuer.
  • Token settings: access tokens default to opaque, and opaque tokens cannot be validated by the shim, so the type was set to JWT on both the application and the machine user. Tokens were RS256 with a key id and a 12-hour lifetime. The refresh-token grant had to be enabled on the application, because the first renewal returned unauthorized_client.
  • Token exchange: the instance's discovery document did not list the token-exchange grant, so it was not used. The shim-minted delegation token was the path used.
  • Tenant B in LiteLLM: a team with a $0.20 budget over one day and the one-model allowlist, holding two keys, tenant-b-user (60 requests per minute) and tenant-b-agent (6 requests per minute), each with 300,000 tokens per minute and a two-day expiry.
  • The first agent run: 3 questions on paper 1902.09666, three calls with status 200, a brief written, per-question F1 of 0.46, 0.17 and 1.00.

The pod 2 line above is rate times hours, and it should be replaced by the billing API's figure once the API catches up.
  • The DigitalOcean invoice was not available at teardown, so the droplet line is rate times hours.
  • The model price applied inside the gateway ($1.9836e-07 per token) meters spend in LiteLLM. Spend recorded in LiteLLM across the run is that metering and has no bearing on any bill.

4.9 Pitfalls and resolutions

  1. Community Cloud had no host with CUDA 12.8 or newer. The create failed with "no longer any instances available". Resolution: the Secure Cloud fallback.
  2. The first pod was replaced at the operator's console. It was stopped and terminated, and an identical pod appeared minutes later. Resolution: the operator confirmed the replacement and it was adopted.
  3. Slow first start. Image extraction, then the first model download and load, then a further wait after each restart for weights and compilation. Health polling must allow for it.
  4. A pod restart reassigns the public TCP port. It changed three times across two restarts. Resolution: gateway/ops/set-pod-port.sh repoints LiteLLM and the egress rule, and each change is in the demo log. An early health poll had checked a stale port.
  5. Wrong audit join key. LiteLLM's spend-log request_id is the response body id, and the x-litellm-call-id header holds a different value. Found at the first join and fixed in the shim. Five exit-gate rows pre-date the fix and have no spend attached.
  6. ZITADEL access tokens were opaque by default. Resolution: access token type JWT on the application and on the machine user.
  7. The refresh-token grant was not enabled on the device-code application. Resolution: enabled in the console.
  8. Token exchange was not advertised by the instance. Resolution: the prepared fallback, a delegation token minted by the shim after validating both credentials.
  9. ZITADEL cannot issue an expired token and always puts the project in the audience. Resolution: a temporary registered test issuer, removed afterward with the registry restored.
  10. A mis-sized team budget test used prompts too short to reach the cap and showed no block. It was repeated with larger prompts. LiteLLM's error text reads "Max budget: 0" although the cap enforced.
  11. The D2 setup failure. Cached tokens are priced at the blended rate, so a 12-call pass costs about $0.0107 and exhausted a $0.05 cap. Resolution: the budget was raised to $1.00 and the passes rerun, as section 4.6 describes.
  12. Egress and DNS. Default-deny needed an explicit allowance for the droplet's resolver, and the resolver appeared three times in the resolver config, so the rules were deduplicated.
  13. Environment values in a pod-create call are plain text. The vLLM API key passed that way sits in the build session's transcript. It was a throwaway key destroyed with the pod.
  14. Billing API lag on the RunPod pod billing read, as section 4.8 describes.

4.10 Scope

This proof of concept exercises the identity layer and the gateway layer. There is no sandbox layer: no consumer code executes on factory infrastructure, so the layer that would isolate tenant-supplied code was reserved, and nothing here supports or contradicts it. Identity paths A, B and C ran live (factory key, federated user, delegated agent), and path D exists as design only in the framework. One model was served. Calls were non-streaming, so streaming accounting is out of scope. The pod was reachable through a public TCP port protected by vLLM's API key only, with the droplet's egress rules pinning the pod address for the LiteLLM container. The delegation path used the shim fallback.

6Reproduce it

This is the condensed path. The configs are in gateway/, the client and test scripts in clients/, the workload in workload/, and the three prompts that drove the build in prompts/. RUN-REPORT.md holds the full record.

Accounts and resources

  • A GPU host that gives you a public TCP port or a private network path. The run used one RTX 4090 on RunPod Secure Cloud. Budget $0.897 per hour at the run's rate, and check current prices.
  • A small VPS for the gateway: 2 vCPU and 4 GB are enough. The run used a DigitalOcean droplet at $0.03571 per hour ($24 per month). The framework notes that a cheaper VPS elsewhere costs about $5 to $6 per month.
  • A free-tier OIDC identity provider for the demo tenant. The run used ZITADEL Cloud. Auth0's free plan and a self-hosted Keycloak are the other options the framework considered.
  • A public DNS name pointing at the VPS (a free subdomain service worked), and a GitHub repository.

Order of operations

  1. Start the model. Launch the vLLM image at version 0.9.0 or later with prefix caching and prompt-token details on, a model length that fits your prompts, and an API key. Confirm that the usage field reports cached tokens, and that two salts separate. workload/phase0_probe.py does this check.
  2. Derive the price. Run the workload sequentially against the pod, measure tokens per hour, and divide the hourly cost by it. Put the result in the LiteLLM config as the model's per-token price, or every budget will read $0.
  3. Stand up the gateway. Copy gateway/env.example and gateway/registry.template.json, fill in secrets on the host only, and bring up gateway/compose.yaml (Caddy, shim, LiteLLM, Postgres). Apply the egress rules in gateway/egress/. Check that only /v1/* answers on the public name.
  4. Add Tenant A. Create a LiteLLM virtual key with the model allowlist, a budget and rate limits, and register its hash. Run clients/phase1_gate.py to confirm the cache salts separate through the full chain.
  5. Add the identity provider. Create the organisation, project, device-code application and machine user. Set the access-token type to JWT and enable the refresh-token grant. Register the issuer, audience, user and agent in the registry. Run clients/phase2_negative.py for the 11 checks.
  6. Run the demos. Use clients/tenant_a_batch.py for D1, clients/d2_cache.py for D2, clients/agent/agent.py for D3, and the SQL in results/d4/audit_reconstruction.sql for D4. Restart the model server before each D2 sequence, and repoint the gateway if the public port changes (gateway/ops/set-pod-port.sh).
  7. Export, then tear down. Export the audit and spend tables, redact configs, and then delete the pod, the droplet and the DNS record. Revoke any tokens you issued.

Expected cost

The run cost about $2.49 in all, as the ledger in section 4.8 shows: about $2.32 for the pod, $0.07 for the failed first pod and $0.10 for the droplet, with $0 for the identity provider, DNS and repository. The cost scales with the hours you leave things running, at $0.897 per hour for the pod and $0.03571 per hour for the droplet. Treat $2 to $3 as the range for a similar run, and the hourly rates as the way to scale it.

7Limits and open questions

Everything the sources flagged as unverified or open is carried here, together with the limits of the run.

Limits of the proof of concept

  • It exercised the identity and gateway layers. There is no sandbox layer, so this run says nothing about isolating tenant-supplied code.
  • Three of four identity paths ran. The trial tier is design only.
  • One model was served, one pod, with non-streaming calls. Streaming accounting is out of scope.
  • The cache salt closes one channel. Tenants still share the scheduler and the GPU, and timing channels beyond the prefix cache are not closed. Dedicated instances are the stronger tier.
  • The budget cap is near-hard. Spend is written after a call completes, so calls in flight can overshoot. In D1 the overshoot was one call, $0.000029.
  • Time to first token did not separate cold from warm at a prefix of about 4.4k tokens. Cached-token counts carry the result, and a timing demonstration needs a longer prefix and more repeats.
  • The pod was reachable on a public port gated only by the vLLM API key. The claim that tenants never reach the pod directly rests on that key.
  • The delegation token used the gateway's fallback. The identity provider's own token exchange and a tenant's real corporate provider are untested.
  • The price is a flat-rate allocation that rests on one sequential client and a mostly cached prefix. It changes with utilization.
  • The workload is three papers and 33 questions. Scores show the workload ran and make no quality claim.
  • The pod 2 cost line is rate times hours, pending the final figure from the RunPod billing API. The droplet line awaits its invoice.

Open questions from the sources

  • The exact hashing construction LiteLLM uses to store virtual keys was not established from primary documentation. The key-storage guidance here is the standard pattern, not a claim about LiteLLM internals.
  • The framework's pricing and tier facts (LiteLLM, identity providers, hosting) are October 2026 snapshots read through a web index, not in a live session. Auth0 changed its free-tier entitlements more than once in 2026.
  • Whether a managed inference endpoint passes cache_salt through, exposes cache-hit metrics and allows an IP allowlist could not be checked for any specific vendor. On an endpoint that does none of these, cache isolation cannot be demonstrated, and it belongs on a vendor-selection checklist.
